# MechWarrior PCS — System GDD: Character Creation (S1)

**Milestone:** m1 — Character creation companion
**Status:** Draft for review
**Engine:** Godot 4.7.2

---

# Purpose

Define the rules contract for the character-creation flow: how a player assigns priorities, spends attribute/advantage/skill points, and ends with a legal, exportable character sheet. This is the only system in the m1 milestone.

The rules are a **port** of the working Python reference at `mw-depo/mw-script/chargen.py`, which is the behavioural oracle. Where the Python is known-buggy, this document defines the corrected behaviour and says so.

---

# Scope

**In scope (m1):** priorities → race → advantages → attributes → characteristics/saving throws → skills → equipment → character sheet (with export).

**Out of scope (later milestones):** the personal-combat tracker, the hex map, creature generation, and the `chargen.py` web front-end.

### Parity oracle — the shipped sample characters are NOT one

`src/data/characters/*.json` were generated by `character_export.py`, which uses a **1e-era schema** (`STRENGTH`/`MEMORY` attributes, `MUSCLES`/`BODY`/`NERVES`/`MIND` characteristics, "Guns (Pistols)" skill names) that does **not** match the 2e rules in `chargen.py` (2e uses `BUILD`/`REFLEX`/`LEARN`/`CHARISMA`/`INTUITION` and `Athletic`/`Physical`/`Mental`/`Social`).

So the sample characters are **legacy artifacts**, kept only because the combat tracker consumes them (it reads HP/armor/weapon). They are **not** a parity oracle for this port.

The parity oracle is instead generated directly from the reference's own functions: `tools/gen_parity_corpus.py` imports `chargen.py` and emits `src/data/parity_corpus.json` — 40 attribute sets with the saving throws and characteristics the reference computes for them. The GDScript engine re-derives the same values and the harness diffs them (S1-AT-14). This is a true cross-check of the port, not a self-consistency check.

# System Rules — S1 Character Creation

## R-S1-1 Priority assignment
The player assigns a **Priority Level 0–4 to each of five categories**: Race, Attributes, Skills, Advantages, Vehicle Class.

- **Standard:** each level 0–4 is used **exactly once** (the five levels total 10).
- **Flexible Priorities** (optional rule, manual p. 15): the player distributes a pool of **10 Character Points** among the five categories, each receiving a level 0–4, the five levels totalling exactly 10. The UI bounds each entry so the pool can always be fully spent.

## R-S1-2 Priority → value table
| Category | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| Race | Human | Human | Clan Warrior | Clan Pilot | Elemental |
| Attributes | 18 | 21 | 24 | 27 | 30 (points) |
| Skills | 8 | 12 | 16 | 20 | 24 (points) |
| Advantages | 0 | 1 | 2 | 3 | 4 (points) |
| Vehicle Class | None | Light | Medium | Heavy | Assault |

## R-S1-3 Races
| Race | Attribute modifiers (BUILD, REFLEX, LEARN, CHARISMA, INTUITION) | Attribute maximums (same order) |
|------|--------------------------------------------------------------|--------------------------------------|
| Human | 0, 0, 0, 0, 0 | 6, 6, 6, 6, 6 |
| Clan Warrior | 0, +1, 0, 0, +1 | 6, 7, 6, 6, 7 |
| Clan Pilot | −1, +2, 0, 0, +1 | 5, 8, 6, 6, 7 |
| Elemental | +2, +1, 0, −1, 0 | 8, 7, 6, 5, 6 |

## R-S1-4 Advantages
Advantages cost **Advantage Points** (0–4 from the priority table).

- **Fixed cost:** Ambidextrous 1, Land Grant 1, Reputation 1, Title (Knight) 1, Title (Baronet) 2, Title (Baron) 3, Toughness 2, Natural Aptitude (Non-Combat Skill) 2, Natural Aptitude (Combat Skill) 3, Sixth Sense 2, Combat Sense 2, Exceptional Attribute 2, Bloodname 3, Enhanced Imaging (EI) Neural Implant 1.
- **Variable cost [1–3]:** Contact, DropShip, Extra Edge, Well-Connected.
- **Tiered families:** Title, Wealth (5k/50k/500k C-Bills), Well-Equipped (1k/5k/25k C-Bills) — **at most one tier per family** may be purchased.
- **Race restrictions:** Bloodname and Enhanced Imaging are Clan/Elemental only. Elementals receive **Toughness free** and cannot buy it again. **Exceptional Attribute is Human only.** DropShip requires Vehicle Class priority 4.
- The Exceptional Attribute choice may exceed that attribute's racial maximum **by 1**.

## R-S1-5 Attribute distribution
The player distributes the Attributes points across BUILD, REFLEX, LEARN, CHARISMA, INTUITION, respecting the racial maximums (plus 1 for an Exceptional Attribute).

- **INTUITION is special:** its *value* is `floor(points / 2) + racial modifier`, so it costs **2 points per point of value**. The UI must bound *points* (not value) so the final score stays at or below the racial maximum.
- **Service eligibility (advisory, not blocking):** Inner Sphere / Secondary Clan MechWarriors need Reflexes or Intuition ≥ 4; Primary Clan MechWarriors need ≥ 5. Characters below the minimum are still buildable and are flagged.

## R-S1-6 Saving throws
`Saving throw = 18 − (2 × attribute value)`, for each of the five attributes, using the **final** (modified) attribute values.

## R-S1-7 Characteristics
| Characteristic | Formula |
|---|---|
| Athletic | 18 − (BUILD + REFLEX) |
| Physical | 18 − (REFLEX + INTUITION) |
| Mental | 18 − (INTUITION + LEARN) |
| Social | 18 − (INTUITION + CHARISMA) |

## R-S1-8 Skills
The player has Skill Points (8–24). **No skill level may exceed the LEARN attribute value.**

- **Skill packages** are offered, filtered by race and by remaining points.
  - **Fixed-skill packages** (Clan races) grant an exact skill/level map.
  - **Flexible-skill packages** (Human) provide *slots* — a count of skills at each level (e.g. 3 at level 2, 3 at level 1) — plus a `required_skills` list (each must take a slot) and `elective_skills` (may be skipped with 0). Level 0 is not a skill level and does not consume a slot.
- Remaining points may be spent on individual skills up to the LEARN cap.
- **Primary Clan Warrior advisory:** Reflexes or Intuition below 5 is flagged, not blocked.

## R-S1-9 Equipment
Three archetypes — **Standard**, **Light**, or **Custom** — each race having its own Standard/Light lists (Clan vs Inner Sphere vs Elemental). Custom lets the player pick individual items from the equipment tables. Purchases deduct from credits (50,000 default).

**A character does not have to spend all of its credits.** The credits are the character's pool; the balance left after the equipment is still the character's, and character creation completes with it unspent. The equipment step is complete whenever the character is not over budget, and nothing requires the balance to reach zero.

## R-S1-10 Character sheet & export
The finished sheet reports: race, attributes (base and final), racial modifiers, saving throws, characteristics, advantages, skills, equipment, and the character's **credit pool**. It must export to JSON with the same shape as the reference `data/characters/*.json` (`version`, `exported`, `character`), so the existing sample characters remain loadable and the future combat tracker can import them.

**The exported `credits` is the character's credit pool, not the balance left after the equipment.** This is the reference schema's meaning, and the reference's own sample characters are the evidence: each stores a fixed pool (5,000 / 25,000 / 50,000) that does not change with what the character carries, and `john_star` carries 22,810 of equipment against a pool of 5,000 — a remaining balance could not be negative. The balance left over is derived: pool − the cost of the equipment.

# Edge Cases

1. **Flexible priorities cannot be spent past the pool** — each entry is bounded so the remaining categories can always absorb the rest.
2. **INTUITION over-max** — the UI must cap *points*, not value, or the final value exceeds the racial maximum.
3. **Exceptional Attribute on a non-Human** — not purchasable; the UI must not offer it.
4. **Toughness on an Elemental** — already included free; the UI must not offer it for purchase.
5. **Two tiers of the same family** (e.g. Title Knight and Title Baron) — blocked; only one tier per family.
6. **Variable-cost advantages** — the player picks a cost tier (1/2/3) that they can afford.
7. **Skill level above LEARN** — rejected with an explanation, not silently clamped.
8. **A flexible package with more required skills than slots** — the required skills consume slots first; an elective that cannot fit is skipped.
9. **Equipment cost exceeding credits** — rejected; the running balance is always visible.
10. **A character whose REFLEX/INTUITION is below the service minimum** — buildable, but flagged on the sheet.

# Known Defects in the Python Reference (the port fixes these)

| ID | Defect | Corrected behaviour |
|----|--------|---------------------|
| P-BUG-1 | `cmd = raw_cmd.upper()` uppercases the whole command line, so `IMPORT <path>` never matches its branch | Case-insensitive **command** comparison only; arguments keep their case |
| P-BUG-2 | Hardcoded absolute path `/home/nicolas/mw-script/data/characters` (stale) | Paths resolved relative to the project/executable, with a clear error when missing |
| P-BUG-3 | Elemental max table reads `maximums` but the code mutates the shared dict for Exceptional Attribute, so the +1 leaks across calls | Racial tables are immutable; the Exceptional bonus is applied to a copy |
| P-BUG-4 | No validation that Flexible Priorities levels total exactly 10 | The pool is enforced per entry, so the total is always 10 by construction |
| P-BUG-5 | The shipped sample characters use a 1e-era schema that contradicts the 2e rules the rest of the script implements | The port implements the 2e schema. The samples are kept as legacy artifacts for the combat tracker; a 2e sample set is generated from the port and covered by the parity corpus |
| P-BUG-6 | `credits` is never initialised in `main()`, but `credits -= equipment_cost` makes it a local, so the equipment step raises `UnboundLocalError` — and `purchase_equipment` never checks a budget anyway, so the reference's credit handling is entirely unenforced | The port gives the character an explicit credit pool, checks every purchase against the balance, and lets the character finish with credits unspent. The exported `credits` is the pool, matching the reference schema's own sample characters |

# UI Contract — the character-creation wizard

## U-S1-1 Step model

The wizard is a **step-by-step flow**, matching the workflow of the source
application (`mw-depo/mw-script/chargen.py`). This was chosen over a single
long scrollable page and over a two-pane layout with a live summary.

- **Why step-by-step:** it mirrors the reference workflow, and it keeps each
  decision in front of the player at a legible size. The scope of this
  application is character generation alone.
- **Why not two-pane:** a live summary pane is the better model for a future
  application in which character generation is only *one* feature alongside
  combat tracking or a hex map, where the player needs to see the character
  while choosing equipment. It is recorded here as the preferred model for
  that later scope, and it is not a cost to move there later: the rules
  engine is already pure and the draft state is already a single object.

## U-S1-2 Steps

| # | Step | Owns | Gate to advance |
|---|------|------|-----------------|
| 1 | Priorities | the five priority categories, standard or flexible | a valid assignment (no duplicate levels, or a flexible total of 10) |
| 2 | Advantages | spending Advantage Points | none — a character may take zero advantages |
| 3 | Attributes | the attribute point pool | **all attribute points spent** |
| 4 | Skills | a skill package, then individual skills | the pool is not overspent |
| 5 | Equipment | archetype loadouts and individual items | the budget is not exceeded |
| 6 | Character sheet | the finished sheet and the export | always |

## U-S1-3 Architecture

- `src/rules/` is **pure and UI-free**. It is the only thing that
  interprets a character.
- `src/ui/character_draft.gd` is the **single state object** carried across
  the steps. The steps read and write it; nothing else holds state.
- `src/ui/wizard.gd` is the **shell**: header, body, message line, and
  footer. It owns navigation and the validation gate; it holds no rules.
- `src/ui/steps/step_*.gd` are the six steps. Each builds its own body and
  reports `is_complete()`.
- The UI is **built in code**, not authored in a `.tscn`. A hand-authored
  scene file for a flow this dynamic is the most likely place for a
  mistake to hide, and the whole tree remains inspectable live through the
  Godot MCP bridge.
- A step is a **container** (U-S1-5) and every step gives the keyboard a
  **focus owner** (U-S1-6). Both are contracts, not implementation
  details: violating either produces controls that exist, are correct,
  and are unreachable by the player.

## U-S1-4 UI acceptance criteria

| ID | Given | When | Then | Method |
|----|-------|------|------|--------|
| UI-AT-1 | A fresh wizard | open it | shows step 1 of 6; Back is disabled; Next is disabled until the step is complete | HARNESS |
| UI-AT-2 | The priorities step | assign a duplicate level, then a valid one | Next stays disabled, then enables; the assignment resolves to the R-S1-2 values | HARNESS |
| UI-AT-3 | The advantages step | buy an advantage | the purchase is recorded and the points are deducted | HARNESS |
| UI-AT-4 | The attributes step | spend the whole pool | the racial modifiers are applied, the derived values are shown, the spin boxes keep the allocated value, and Next enables | HARNESS |
| UI-AT-5 | The skills step | buy a package | the skills are granted, the package name is recorded, and the individual skill list is populated | HARNESS |
| UI-AT-6 | The equipment step | buy an archetype, then remove an item | the credits are deducted and refunded | HARNESS |
| UI-AT-7 | The last step | finish | the character is written to `user://character.json` and the file has the R-S1-10 export shape | HARNESS |

**Why UI-AT-4 checks the spin box value explicitly:** Godot's `SpinBox`
clamps its value to `max_value`. A maximum computed from the *remaining
headroom* rather than from the points already allocated silently destroys
the player's allocation. The harness asserts the value survives.

## U-S1-5 Layout contract

A step is a **container**, not a bare `Control`.

- A plain `Control` has a zero minimum size and does not lay out its own
  children. A step built that way is given zero height by the body, and
  every control inside it is clipped out of existence: still in the tree,
  but neither visible nor clickable.
- The wizard sets `SIZE_EXPAND_FILL` on the step it creates.
- A step's own top-level child fills the step's width.
- **A step has exactly one scroll container.** A `ScrollContainer` nested
  inside another one has a minimum height of zero — it can always scroll —
  so the inner one collapses and takes its whole content with it. Where
  a second region is needed, it is a plain container inside the step's
  one scroll.

**Why this is a contract and not an implementation detail:** every one of
these rules was violated at least once, and every violation produced the
same symptom — the controls existed and were correct, but the player
could not see or reach them. UI-AT-8 measures the layout rather than
trusting it.

## U-S1-6 Input contract

- **Every step gives the keyboard a focus owner.** Without one, Enter and
  Space go nowhere: the player must click a control before the keyboard
  can reach it.
- **Focus lands on the first *value* control** — a dropdown, a spin box, a
  text field — not merely the first focusable control. On the priorities
  step the first focusable control is the "Flexible Priorities" checkbox,
  and a player pressing Enter to open the first dropdown would instead
  silently switch the priority mode.
- **A focused dropdown answers the arrow keys directly.** A plain
  `OptionButton` only changes its value through its popup, which splits
  the keyboard path into three steps and behaves inconsistently: a popup
  opened with the mouse starts its highlight on "no item", so the first
  arrow press lands on the first entry rather than moving one step from
  the current value. `src/ui/level_option.gd` fixes this.
- **A value control reports its value even when it is unchanged.** A
  dropdown only emits a change, so a category the player leaves alone —
  or one set to the value it already shows — would never be recorded.
  The priorities step therefore records all five categories from the
  start, at their default of 0. Without this, "Priority 0" could never
  be chosen, and since the assignment needs all five categories, a
  single untouched row left the whole character unresolved.
- A read-only `RichTextLabel` must not take focus (`FOCUS_NONE`).
- **A `SpinBox` cannot take focus itself** — its `focus_mode` is `FOCUS_NONE`
  and the player types into the line edit inside it. Focusing the SpinBox
  warns and does nothing, so the line edit is focused instead.

## U-S1-7 A value control's maximum is its absolute cap

A control that holds a **total** must be bounded by the absolute cap for
that value, not by the headroom — the amount that may still be *added*.

The attribute fields are the case in point. The field shows the total
points in the attribute, and its maximum is the racial cap in points:
`maximum - modifier` for a normal attribute and `2 * (maximum - modifier)`
for INTUITION, which costs two points per point of value. Bounding the
field by the headroom instead caps it at `cap - already spent`: a
character whose racial maximum was 6 could never go past 3 once 3 points
were in, and the remaining 3 points were unreachable. The player sees a
field that stops at 3 and no way to spend the rest of the character.

The pool still bounds the field: the points already spent on the *other*
attributes are not available here. The two bounds are independent — the
racial cap limits one attribute, the pool limits the character — and the
field's maximum is the smaller of the two.

This matches the reference implementation, which asks for an *increment*
(`max_points_to_assign`) bounded by `max_value - modifier` for a normal
attribute and `2 * (max_value - modifier) - assigned` for INTUITION.

# Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Port diverges from the Python reference | High | The Python is the oracle; parity is asserted by running both over a shared corpus and diffing outputs |
| The Python reference itself is wrong in places | Medium | Defects found are recorded above (P-BUG-1..4) and the port implements the corrected behaviour |
| Rulebook ambiguity (e.g. Clan Heritage, trueborn Bloodnames) | Medium | Out of scope for m1 and explicitly flagged as unimplemented, not guessed |
| UI drift from the rules engine | High | The engine is pure logic with no UI dependency; the wizard only calls it |
| The wizard's own state drifts from the draft | Medium | The draft is the single source of truth; the steps hold no state of their own, and the UI harness drives the real controls rather than the draft directly |
